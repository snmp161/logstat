# logstat

[English](README.md) | **Русский**

Демон, который непрерывно читает пишущийся текстовый лог-файл, ищет в каждой строке заданные кодовые слова и ведёт в Redis инкрементные счётчики по каждому слову. Счётчик растёт со временем и по расписанию (по умолчанию раз в сутки в полночь) обнуляется — внешний считыватель снимает значение по этому циклу. Самосброс отключаем.

Демон не привязан ни к nginx, ни к формату лога: он работает с сырыми строками и матчит подстроку. Один процесс = один лог-файл; несколько логов на хосте обслуживаются несколькими инстансами шаблонного systemd-юнита.

Реализация: Go, статический бинарник (`CGO_ENABLED=0`), конфигурация — YAML.

**Состояние проекта: функционально закончен, режим поддержки.** logstat делает
одну вещь — считает кодовые слова в одном лог-файле и ведёт итоги в Redis, — и
делает её. Новых возможностей не планируется: несколько логов в одном процессе,
TLS до Redis, Sentinel и Cluster, push-модель метрик и перечитывание конфига на
лету [сознательно вне рамок](docs/specification.md). Сообщения об ошибках и
исправления безопасности принимаются; аргументация всех принятых решений — в
[`docs/specification.md`](docs/specification.md).

## Как это работает

1. Демон открывает лог-файл в режиме «`tail -F`». Существующий файл открывается **в конце** (аналог `tail -n0`) — то, что записано до старта, не считается. Если файла ещё нет (ПО-источник может подняться позже), демон не падает, а ждёт его появления и читает **с начала** появившегося файла.
2. Для каждой новой строки проверяется вхождение каждого кодового слова: **подстрока в любом месте строки**, по умолчанию регистрозависимо, а при `case_sensitive: no` — регистронезависимо ([подробнее](#регистрозависимость)). Счёт **по строке, не по вхождению** — слово встретилось в строке дважды, счётчик +1. Два разных слова в одной строке — инкрементится каждое.
3. Инкременты копятся в памяти и сбрасываются в Redis пачкой раз в `flush_interval` секунд, а не на каждую строку. При сбросе: `INCRBY` целочисленного счётчика, затем — если включён `heartbeat_key` — `SET` форматированного heartbeat-значения с новым итогом из ответа `INCRBY`.
4. Ротация лога проходится прозрачно, поддержаны оба режима logrotate: `create` (rename + новый файл, смена inode) и `copytruncate` (усечение на месте). Строки не теряются и не пересчитываются дважды.
5. По cron-расписанию `reset.schedule` счётчики обнуляются: сначала флашится остаток буфера (строки завершающегося интервала попадают в него), затем `SET counter 0` и запись heartbeat-значения `lines=0`.
6. Redis может быть недоступен (в т.ч. удалённый) — буфер копится в памяти, демон не падает и не теряет счёт, при восстановлении досбрасывает. Об аварии сообщается в лог один раз (повторы — на уровне `debug`), о восстановлении — тоже. Убедившись, что соединения нет, флаш прекращает обход остальных слов, чтобы не ждать таймаут подключения на каждое: время флаша и остановки демона не растёт с числом слов. Внутренние сообщения `go-redis` тоже уходят в лог демона (уровень `debug`), а не в stderr.
7. По `SIGTERM`/`SIGINT` остаток буфера флашится и процесс выходит с кодом 0.
8. При `metrics.enabled: true` демон дополнительно отдаёт по HTTP свои [метрики Prometheus](#метрики-prometheus): uptime, конфигурацию, с которой запущен, счётчики по кодовым словам этого процесса и итоги по словам, прочитанные из Redis. Корень того же порта показывает те же цифры в виде [статус-страницы](#статус-страница) для браузера.

Оффсет файла между рестартами **сознательно не персистится**: счётчик живёт в Redis, поэтому рестарт не теряет накопленное, но строки, записанные за время простоя демона, не досчитываются.

## Ключи в Redis

`<host>` — короткое имя хоста (эквивалент `hostname -s`), `<action>` — кодовое слово.

| Назначение | Ключ | Значение | Операция | Условие |
|---|---|---|---|---|
| Служебный счётчик | `logstat:counter:<host>:<action>` | целое число | `INCRBY` / `SET 0` | всегда |
| Значение для мониторинга (heartbeat) | `logstat:heartbeat:<host>:<action>` | `server=<host> time=<iso8601> type=<action> lines=<N>` | `SET` | `heartbeat_key: true` |

Оба ключа живут `redis.ttl` секунд (по умолчанию сутки), см. [TTL на ключи](#ttl-на-ключи).

Пример heartbeat-значения:

```
server=web01 time=2026-08-19T15:04:05+03:00 type=get-sms lines=1274
```

Время — ISO-8601 с таймзоной, совместимо с `date -Iseconds`.

Ключей два потому, что атомарно инкрементить форматированную строку нельзя: счёт ведётся на целочисленном ключе, а `<N>` для heartbeat-значения берётся из ответа `INCRBY`.

При старте отсутствующие ключи создаются через `SET ... NX` (счётчик — нулём, heartbeat — с текущим итогом счётчика), существующие **не затираются**: рестарт демона не сбрасывает накопленное. Благодаря этому внешний считыватель видит ключи сразу после установки, ещё до первого совпадения.

**Heartbeat-ключ можно отключить.** При `heartbeat_key: false` демон ведёт только целочисленные счётчики: heartbeat не создаётся при инициализации, не пишется при флаше и не трогается при сбросе, включая `logstat clear`. Уже существующий ключ при выключении параметра **не удаляется** — обновления просто прекращаются, подчистить его при необходимости надо самому:

```sh
redis-cli --scan --pattern 'logstat:heartbeat:*' | xargs -r redis-cli del
```

**Миграция с v0.1.0.** В v0.1.0 ключ мониторинга назывался `logstat:<host>_type=<action>`. Начиная с v0.2.0 это `logstat:heartbeat:<host>:<action>`: обновите шаблон в считывателе и удалите старые ключи, демон их не тронет.

```sh
redis-cli --scan --pattern 'logstat:*_type=*' | xargs -r redis-cli del
```

Целочисленные счётчики `logstat:counter:<host>:<action>` не изменились — накопленные значения при обновлении не теряются.

### TTL на ключи

`redis.ttl` (секунды, дефолт `86400` — сутки, `0` — без TTL) задаёт срок жизни обоих ключей. TTL **скользящий**: он переставляется при каждом флаше, в том числе когда флашить нечего.

Так сделано потому, что `INCRBY` в Redis не продлевает TTL сам: с «одноразовым» TTL ключ активно используемого счётчика умер бы посреди цикла и счёт молча начался бы с нуля. Поэтому TTL здесь измеряет не «сколько живёт ключ», а **сколько ключ переживает демона**:

- пока инстанс работает, ключи не истекают — TTL продлевается каждые `flush_interval` секунд;
- когда инстанс исчез (хост выведен, конфиг удалён, слово убрано из `actions`), его ключи уходят сами через `redis.ttl` и не копятся в Redis мусором.

`redis.ttl` должен быть **больше** `flush_interval`, иначе ключи успеют истечь между двумя флашами — при валидации на это выдаётся предупреждение.

При `redis.ttl: 0` TTL не ставится, а уже проставленный снимается: один раз при старте демон выполняет `PERSIST`, поэтому выключение параметра обратимо без ручной чистки.

## Конфигурация

Путь к конфигу — флаг `--config /etc/logstat/config.yaml` (короткий `-c`). Значения по умолчанию встроены: при отсутствии поля берётся дефолт. Пример со всеми полями — [`packaging/default.yaml`](packaging/default.yaml).

```yaml
log_path: /var/log/app.log

actions:
  - get-number
  - get-sms
  - getNumber
  - getStatus

case_sensitive: yes
flush_interval: 10
poll: false
heartbeat_key: true
lock_file: /run/logstat/default/logstat.lock

redis:
  host: 127.0.0.1
  port: 6379
  db: 0
  password: ""
  ttl: 86400

logging:
  level: info
  output: journald
  file: ""

reset:
  enabled: true
  schedule: "0 0 * * *"

metrics:
  enabled: false
  listen: 127.0.0.1:9843
  path: /metrics
```

| Параметр | Тип | Дефолт | Назначение |
|---|---|---|---|
| `log_path` | string | `/var/log/app.log` | путь к лог-файлу |
| `actions` | list\<string\> | `[get-number, get-sms, getNumber, getStatus]` | кодовые слова |
| `case_sensitive` | bool | `true` | учитывать регистр при матчинге; `no` — совпадение в любом регистре |
| `flush_interval` | int (сек) | `10` | период сброса буфера в Redis |
| `poll` | bool | `false` | поллинг вместо inotify (для сетевых ФС) |
| `heartbeat_key` | bool | `true` | вести heartbeat-ключ `logstat:heartbeat:<host>:<action>` |
| `lock_file` | string | `/run/logstat/logstat.lock` | lock-файл инстанса (уникальный на конфиг) |
| `redis.host` | string | `127.0.0.1` | хост Redis (может быть удалённым) |
| `redis.port` | int | `6379` | порт Redis |
| `redis.db` | int | `0` | номер БД Redis |
| `redis.password` | string | `""` | `AUTH`, если задан `requirepass` |
| `redis.ttl` | int (сек) | `86400` | TTL ключей (скользящий); `0` — без TTL |
| `logging.level` | string | `info` | `debug` / `info` / `warn` / `error` |
| `logging.output` | string | `journald` | `journald` (stderr) или `file` |
| `logging.file` | string | `""` | путь лог-файла при `output: file` (уникальный на конфиг) |
| `reset.enabled` | bool | `true` | включить самосброс |
| `reset.schedule` | string | `"0 0 * * *"` | cron-расписание сброса (стандартный 5-польный) |
| `metrics.enabled` | bool | `false` | поднимать эндпоинт метрик Prometheus |
| `metrics.listen` | string | `127.0.0.1:9843` | `host:port` экспортера (уникальный на конфиг) |
| `metrics.path` | string | `/metrics` | путь эндпоинта метрик |

### Регистрозависимость

`case_sensitive` определяет, как подстрочный поиск сравнивает кодовое слово со строкой лога. Это обычный YAML-булев, поэтому `yes`/`no` принимаются наравне с `true`/`false`.

| Значение | Поведение |
|---|---|
| `yes` (дефолт) | сравнение байт в байт: `get-number` совпадёт только с `get-number`, но не с `GET-NUMBER` и не с `Get-Number` |
| `no` | перед поиском и строка, и кодовые слова приводятся к нижнему регистру, поэтому любое написание слова идёт в один счётчик |

```yaml
actions:
  - get-number
case_sensitive: no
```

С таким конфигом все три строки ниже дают +1 счётчику `get-number`:

```
"GET /api/get-number?x=1 HTTP/1.1" 200
"GET /api/GET-NUMBER?x=1 HTTP/1.1" 200
"GET /api/Get-Number?x=1 HTTP/1.1" 200
```

Дефолт — `yes`, так что уже существующий конфиг работает ровно так же, как до появления параметра.

Регистр влияет **только на матчинг**. Ключи Redis и heartbeat-значение всегда содержат слово в том написании, в каком оно задано в `actions`, а не в том, в каком встретилось в строке: `logstat:counter:<host>:get-number` остаётся единственным ключом этого слова при любом написании в логе, а переключение параметра не переносит уже идущий счёт на другой ключ.

Что стоит знать перед выключением регистрозависимости:

- Префиксные пересечения тоже начинают считаться без учёта регистра, поэтому пара вида `getstatus` / `GetStatusExtended` даст предупреждение при старте, хотя в регистрозависимом режиме молчит.
- Слова, различающиеся **только** регистром (`getNumber` и `GETNUMBER`), всегда совпадают вместе, но пишутся в два разных ключа Redis — это почти наверняка ошибка конфига. Демон предупреждает о такой паре и оставляет оба слова: молча выкинуть одно значило бы бросить ключ, который, возможно, уже читает считыватель.

**Расписание сброса.** `reset.schedule` — стандартный 5-польный cron (`минута час день месяц день_недели`), часовой пояс локальный для хоста, срабатывание всегда в `:00` секунд целевой минуты. Никакой самописной логики времени нет, поэтому гибкость получается бесплатно:

| Выражение | Смысл |
|---|---|
| `0 0 * * *` | раз в сутки в полночь (дефолт) |
| `1 * * * *` | 1-я минута каждого часа |
| `*/30 * * * *` | каждые полчаса |
| `0 */6 * * *` | каждые 6 часов |

Также принимаются дескрипторы вида `@daily`, `@hourly`. Шестипольный синтаксис с секундами **не** принимается сознательно.

При `reset.enabled: false` демон только считает; обнуление выполняет кто-то снаружи (внешний скрипт/таймер или ручной `logstat clear`).

Граница интервала держится, только пока Redis доступен. Если расписание сработало во время аварии, финальный флаш не проходит, сброс откладывается, и при восстановлении порядок получается «сначала обнуление, потом досброс»: строки завершившегося интервала попадают в новый. Альтернатива — выбросить их, а сдвинуть данные на один интервал лучше, чем потерять.

**Валидация при старте.** Конфиг парсится строго: неизвестные поля — ошибка. Проверяется, что `actions` непустой, `flush_interval > 0`, `lock_file` задан и его каталог создаваем, `reset.schedule` — валидное 5-польное cron-выражение, `logging.level` и `logging.output` из допустимого набора, при `output: file` поле `logging.file` непустое и путь записываем. `metrics.listen` должен разбираться как `host:port` с портом в 1..65535, `metrics.path` — начинаться со слэша и не содержать фигурных скобок и пробелов; всё это проверяется независимо от того, включён ли экспортер, чтобы опечатка не дождалась дня, когда его включат. Валидация не останавливается на первой проблеме: конфиг проверяется целиком и все фатальные ошибки сообщаются разом через `; `, чтобы пара опечаток не превращалась в цикл «поправил — перезапустил — увидел следующую». Значения `poll`, `heartbeat_key`, `case_sensitive` и `metrics.enabled` должны быть булевыми, `redis.ttl` — неотрицательным. Фатальная ошибка конфига — выход с ненулевым кодом (systemd покажет в статусе). Дубликаты в `actions`, слова, являющиеся подстрокой другого, и — при `case_sensitive: no` — слова, различающиеся только регистром, дают предупреждение в лог, но не мешают старту.

## CLI

```
logstat run   --config <path>                 демон (основной режим)
logstat clear --config <path> --all           обнулить все счётчики конфига
logstat clear --config <path> --action <word> обнулить один счётчик
logstat version                               версия, commit, дата сборки
logstat --help                                справка
```

`clear` работает всегда, независимо от `reset.enabled`, и обнуляет и целочисленный счётчик, и heartbeat-значение (`lines=0`; при `heartbeat_key: false` heartbeat не трогается). `--action` принимает только слово, перечисленное в `actions` этого конфига — так опечатка не создаст мусорный ключ. Сверка со списком идёт точным сравнением независимо от `case_sensitive`: параметр управляет поиском в логе, а не именами ключей.

Коды возврата: `0` — успех, `1` — ошибка выполнения (конфиг, lock, Redis), `2` — ошибка использования.

## Сборка

Нужен Go (версия зафиксирована в `go.mod`). `CGO_ENABLED=0` выставляется автоматически.

```sh
make build          # статический бинарник для текущей архитектуры → dist/logstat
make build-all      # linux/amd64 + linux/arm64 → dist/logstat_linux_<arch>/logstat
make test           # go test -race ./...
make cover          # тесты с профилем покрытия
make fuzz           # фаззинг конфига (FUZZTIME=1m)
make soak           # долгий прогон против живого Redis (DURATION=10m)
make lint           # gofmt + go vet + golangci-lint
make package        # .deb и .rpm для обеих архитектур (нужен nfpm)
make tools          # поставить пиновые nfpm и golangci-lint в GOPATH/bin
make clean
make help
```

Версия, commit и дата сборки вшиваются через `-ldflags` и видны в `logstat version`. По умолчанию версия берётся из `git describe`; можно задать явно: `make build VERSION=v1.2.3`.

Пакеты собираются через [nfpm](https://github.com/goreleaser/nfpm) из готового бинарника — один [`nfpm.yaml`](nfpm.yaml) на оба формата. Релизы собирает GoReleaser по [`.goreleaser.yaml`](.goreleaser.yaml): при пуше тега `v*` workflow [`release.yml`](.github/workflows/release.yml) публикует GitHub Release с бинарниками, `.deb`, `.rpm` и checksums. На каждый push и PR workflow [`ci.yml`](.github/workflows/ci.yml) прогоняет lint, `go test -race` с покрытием, кросс-сборку и сборку пакетов.

## Установка пакета

```sh
# Debian / Ubuntu
sudo dpkg -i logstat_<version>-1_amd64.deb

# RHEL / Alma / Rocky
sudo rpm -i logstat-<version>-1.x86_64.rpm
```

Пакет ставит:

- `/usr/bin/logstat` — статический бинарник;
- `/etc/logstat/default.yaml` — пример конфига как conffile / `%config(noreplace)`, при обновлении правки не затираются;
- `/lib/systemd/system/logstat@.service` (на rpm-дистрибутивах — `/usr/lib/systemd/system/logstat@.service`) — шаблонный юнит;
- postinstall создаёт системного пользователя `logstat`, делает `systemctl daemon-reload` и `try-restart 'logstat@*.service'`, чтобы после обновления работавшие инстансы поднялись на новом бинарнике.

Дальше — свой конфиг на каждый лог и запуск инстанса:

```sh
sudoedit /etc/logstat/app1.yaml
sudo systemctl enable --now logstat@app1.service
systemctl status 'logstat@*'
journalctl -u logstat@app1 -f
```

Юнит намеренно **не** зависит ни от Redis, ни от nginx (только `network-online.target`): Redis может быть на другой машине, буфер в памяти переживает его недоступность, а источник лога произволен. При `reset.enabled: true` никакие таймеры и clear-сервисы не нужны.

## Мультиконфиг и мультиинстанс

Юнит шаблонный: экземпляр `logstat@<имя>` читает `/etc/logstat/<имя>.yaml`. Так `logstat@app1` парсит `/etc/logstat/app1.yaml`, `logstat@nginx` — `/etc/logstat/nginx.yaml`. Одиночный кейс — просто один инстанс, например `logstat@default` с `/etc/logstat/default.yaml`.

При нескольких инстансах на одном хосте:

- у каждого конфига **свой** `lock_file`, иначе второй инстанс не стартует из-за `flock`. Юнит выдаёт каждому инстансу свой рантайм-каталог (`RuntimeDirectory=logstat/%i` → `/run/logstat/<инстанс>`), поэтому естественный путь — `/run/logstat/<инстанс>/logstat.lock`. Это единственный каталог, доступный демону на запись при `ProtectSystem=strict`;
- при `logging.output: file` — **свой** `logging.file` у каждого;
- при `metrics.enabled: true` — **свой** порт в `metrics.listen`: занятый порт валит старт инстанса;
- если инстансы смотрят в **один и тот же** Redis (host/port/db), их наборы `actions` не должны пересекаться — иначе коллизия ключей (см. [Предупреждения оператору](#предупреждения-оператору)). Разный Redis или разный `db` снимают вопрос сами по себе.

Раскатка — через Salt (`file.managed` для пакета и per-инстансных конфигов + `service.running` по списку инстансов) либо установка `.deb` / `.rpm` из GitHub Release.

## Метрики Prometheus

Демон умеет отдавать свои метрики по HTTP. Экспортер **по умолчанию выключен**: апгрейд не должен открывать слушающий сокет там, где его не ждали, а два инстанса на одном хосте иначе подрались бы за один порт.

```yaml
metrics:
  enabled: true
  listen: 127.0.0.1:9843   # только петля; наружу выставляем осознанно
  path: /metrics
```

```console
$ curl -s localhost:9843/metrics | grep -v '^#' | grep logstat_

logstat_config_case_sensitive 1
logstat_config_flush_interval_seconds 10
logstat_config_heartbeat_key 1
logstat_config_info{host="app1",log_path="/var/log/app.log",...} 1
logstat_config_poll 0
logstat_config_redis_ttl_seconds 86400
logstat_config_reset_enabled 1
logstat_lines_read_total 12043

logstat_redis_counter{action="get-number"} 8125

```

|---|---|---|---|
| `logstat_uptime_seconds` | gauge | — | сколько работает этот процесс |
| `logstat_start_time_seconds` | gauge | — | unix-время старта |
| `logstat_config_info` | gauge | `log_path`, `host`, `redis_addr`, `redis_db`, `redis_password_set`, `logging_output`, `reset_schedule` | всегда `1`; конфигурация, с которой запущен инстанс |
| `logstat_config_flush_interval_seconds` | gauge | — | `flush_interval` |
| `logstat_config_redis_ttl_seconds` | gauge | — | `redis.ttl`, `0` — без TTL |
| `logstat_config_case_sensitive` | gauge | — | `case_sensitive`, `1`/`0` |
| `logstat_config_poll` | gauge | — | `poll`, `1`/`0` |
| `logstat_config_heartbeat_key` | gauge | — | `heartbeat_key`, `1`/`0` |
| `logstat_config_reset_enabled` | gauge | — | `reset.enabled`, `1`/`0` |
| `logstat_config_actions` | gauge | — | сколько кодовых слов в конфиге |
| `logstat_lines_read_total` | counter | — | прочитано строк лога с момента старта |
| `logstat_matched_lines_total` | counter | `action` | совпадений по слову с момента старта (внутренний счётчик) |
| `logstat_pending_increments` | gauge | `action` | лежит в буфере, ещё не сброшено в Redis |

### Статус-страница

Корень того же порта отдаёт сводку для человека — то, ради чего в браузер и заходят, в отличие от сырого текста экспозиции:

```
logstat v0.3.0 · app1                                            /metrics →
──────────────────────────────────────────────────────────────────────────
up 1h 02m (since 2026-08-22 15:04:05 MSK) · redis 127.0.0.1:6379 db 0 · up

code words
  word                              in memory   buffered   in redis
  get-number                              417          3       8125
  get-sms                                  12          0        903
  getNumber                                 0          0          0
  getStatus                                41          1          —

configuration
  log_path          /var/log/app.log
  lock_file         /run/logstat/app1/logstat.lock
  case_sensitive    yes
  flush_interval    10s
  poll              no
  heartbeat_key     yes
  redis.ttl         24h0m0s
  redis.password    not set
  reset             0 0 * * *
  logging           info → journald
  metrics.listen    127.0.0.1:9843

rendered 2026-08-22 16:06:07 MSK · reload to refresh
```

Это сводка на один экран, а не дашборд: ни графиков, ни истории, ни автообновления (страница обновляется перезагрузкой — забытая вкладка не должна долбить Redis), и ничего, что меняло бы состояние демона. Графики и алерты — работа Prometheus и Grafana.

Три колонки по каждому слову — это три числа, которые могут разойтись, рядом: «в памяти» — сколько совпадений насчитал этот процесс с момента старта, «в буфере» — сколько ждёт ближайшего флаша, «в redis» — общий итог, который видит внешний считыватель. Отсутствующий ключ показывается прочерком, а не нулём, — ровно как он отсутствует в метриках. При недоступном Redis страница всё равно рисуется и сообщает об этом в шапке. Шапка живёт по тем же правилам, что и `logstat_redis_up`: «недоступен» означает, что Redis не ответил, а отдельный ключ с нечитаемым значением показывается прочерком в своей строке и пометкой рядом со статусом.

Как и метрики, страница никогда не показывает пароль Redis — только факт, задан он или нет.

При `metrics.path: /` корень занимает экспозиция метрик, она отдаётся **на любом пути**, и статус-страницы нет. Хвостовой слэш запрещён по той же причине: для `net/http` шаблон `/metrics/` — это поддерево, и метрики отвечали бы ещё и на `/metrics/что-угодно`.

Путь понимается буквально. Фигурные скобки и пробелы валидация отвергает: маршрутизатор `net/http` читает `{...}` как подстановку — `/{env}` отдавал бы метрики на любом односегментном пути, — а на сломанном шаблоне вроде `/met{rics` просто паникует. Экспортер повторяет проверку на своём входе, чтобы никакой вызов не мог уронить процесс паникой вместо ошибки конфигурации.

**Пароль Redis в метриках не появляется.** Лейбл `redis_password_set` сообщает только `true`/`false` — задан ли вообще `requirepass`-пароль в конфиге.

**Два счётчика по каждому слову меряют сознательно разное.** `logstat_matched_lines_total` — собственный счётчик процесса: монотонный с момента старта, обнуляется рестартом, не зависит ни от Redis, ни от `reset.schedule`; именно его надо брать в `rate()`. `logstat_redis_counter` — то, что видит внешний считыватель: общий на хост+слово, переживает рестарт демона и обнуляется по `reset.schedule`; пилообразный, для `rate()` не годится. Расхождение между ними — само по себе сигнал: Redis недоступен, ключ истёк по TTL или счётчик обнулили снаружи.

Каждое настроенное слово присутствует в `logstat_matched_lines_total` и `logstat_pending_increments` с самого старта, нулём, — чтобы «слово настроено, но ни разу не встретилось» не выглядело как «слово не настроено».

Значения `logstat_redis_counter` читаются **на скрейпе**, одним `MGET` с таймаутом 2 с (заведомо меньше типичного `scrape_timeout`). Скрейп не висит и не роняет демон: при недоступном Redis эндпоинт всё равно отвечает, но `logstat_redis_up` равен `0`, серий `logstat_redis_counter` в ответе нет, а `logstat_redis_scrape_errors_total` растёт. Отсутствующий ключ — это отсутствующая серия, а не `0`: выдуманный ноль неотличим от честно обнулённого счётчика.

`logstat_redis_up` отвечает ровно на один вопрос: ответил ли Redis. Нечисловое значение в ключе (в него пишет кто-то ещё) авария связи не означает — `up` остаётся `1`, это слово пропускается как отсутствующее, остальные экспортируются как обычно, а факт виден в `logstat_redis_scrape_errors_total` и в логе демона. Иначе одна чужая запись гасила бы всю картину и выглядела бы недоступностью Redis.

**Ошибка bind фатальна.** Если `metrics.enabled: true`, а порт занят, демон выходит с ненулевым кодом и systemd показывает причину в статусе. Молча работать без метрик, которые явно включили, хуже: мониторинг увидел бы тишину и решил, что всё в порядке. Сокет открывается **до** начала чтения лога, поэтому падение происходит сразу, а не после первого флаша.

**Смерть экспортера в работе — тоже.** Если HTTP-сервер завершится с ошибкой уже после старта, демон флашит остаток буфера и выходит с ненулевым кодом, а не продолжает считать без метрик: аргумент тот же, просто отложенный. Штатная остановка сервера при завершении демона ошибкой не считается.

Таймауты этого сервера: `ReadHeaderTimeout` 5 с, `WriteTimeout` 30 с, `IdleTimeout` 60 с. Таймаут записи заведомо больше двухсекундного чтения Redis, поэтому медленный Redis не рвёт скрейп на середине.

Скрейп-конфиг для хоста с несколькими инстансами:

```yaml
scrape_configs:
  - job_name: logstat
    static_configs:
      - targets: ["app1.example.com:9843", "app1.example.com:9844"]
```

**Прежде чем выставлять порт наружу.** На эндпоинте нет ни TLS, ни аутентификации, ни rate-limit — всё это сознательно вне рамок, а дефолтный `listen` слушает только петлю. Любой, кто дотянется до порта, прочитает путь к логу, lock-файл, адрес и номер БД Redis, кодовые слова, расписание и версию, а каждое открытие страницы стоит одного `MGET` в Redis. Внутри процесса остаётся только пароль. Если метрики должны уйти с хоста — ставьте перед ними firewall или reverse proxy с TLS и аутентификацией, а не `0.0.0.0` в надежде на лучшее.

## Логирование самого демона

Демон ведёт собственный лог: старт и стоп, загруженный конфиг, факт и результат каждого флаша, срабатывание сброса, недоступность Redis и реконнект, ротация лог-файла, ошибки. Формат человекочитаемый — таймстамп, уровень, сообщение, атрибуты:

```
2026-08-18T15:04:05+03:00 INFO  starting log_path=/var/log/app.log actions=4 flush_interval=10 ...
2026-08-18T15:04:15+03:00 WARN  redis unavailable, buffering in memory op=incrby error="..."
```

События по отдельным строкам лога пишутся только на уровне `debug` — на высоком RPS это слишком шумно.

- `logging.output: journald` (дефолт) — вывод в **stderr**, откуда systemd складывает в journald: `journalctl -u logstat@<инстанс>`. Отдельной интеграции с протоколом journald не требуется.
- `logging.output: file` — вывод в файл `logging.file`. Ротацию этого файла обеспечивает внешний logrotate; демон переоткрывает свой лог по `SIGHUP`, что для logrotate удобно оформить как `postrotate systemctl reload logstat@<инстанс>` (юнит содержит `ExecReload=/bin/kill -HUP $MAINPID`).

  Важно: при `ProtectSystem=strict` каталог `/var/log` доступен только для чтения. Чтобы писать туда, добавьте в юнит (лучше через drop-in) `LogsDirectory=logstat` — systemd создаст `/var/log/logstat`, доступный на запись:

  ```sh
  sudo systemctl edit logstat@app1.service
  # [Service]
  # LogsDirectory=logstat
  ```

## Права на чтение лога

Демон работает под непривилегированным пользователем `logstat` с systemd-хардненингом (`NoNewPrivileges`, `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`). Группа, нужная для чтения лога, зависит от владельца файла: для nginx это обычно `adm` (в юните так и стоит), для другого ПО `SupplementaryGroups` надо подогнать под конкретный лог — иногда демону хватит обычных прав, если файл читаем всем.

```sh
ls -l /var/log/app.log            # посмотреть владельца и группу
sudo systemctl edit logstat@app1.service
# [Service]
# SupplementaryGroups=
# SupplementaryGroups=<нужная группа>
```

## Предупреждения оператору

**Префиксные пересечения в `actions`.** Матчинг подстрочный, поэтому слово, являющееся частью другого слова из списка, инкрементит оба счётчика: `getStatus` совпадёт и внутри гипотетического `getStatusExtended`. Среди четырёх дефолтных слов пересечений нет (ни одно не является подстрокой другого). При добавлении новых слов это надо проверять — при старте демон выдаёт предупреждение в лог на каждую такую пару, но работать не отказывается. При [`case_sensitive: no`](#регистрозависимость) пересечение считается без учёта регистра, поэтому пересекающимися становятся и пары вроде `getstatus` / `GetStatusExtended`.

**Потенциальная коллизия ключей.** Ключи содержат только `<host>` и `<action>`. Коллизия возможна ровно в одном сценарии: несколько инстансов на одном хосте, у которых в конфиге **один и тот же** Redis (host/port/db) **и** пересекающиеся `actions` — тогда они пишут в общий ключ и затирают друг друга. Обычно этого не бывает: у разных конфигов, как правило, и Redis разный (свой host/db в каждом), а если Redis один — достаточно непересекающихся наборов `actions`. Софт этот случай **не предотвращает**, это ответственность оператора.

**Строки за время простоя не досчитываются.** Оффсет файла между рестартами не персистится сознательно (ради простоты): после рестарта демон встаёт в конец файла, а счётчик продолжается с текущего значения в Redis.

**Ротация в режиме `copytruncate` принципиально гоночная.** Между копированием и усечением файла ПО-источник может успеть записать строки, которые пропадут для всех читателей. Если ротацией управляете вы — предпочтительнее режим `create`.

## Удаление пакета

Enable-симлинки инстансов (`/etc/systemd/system/*.wants/logstat@<имя>.service`) создаёт администратор командой `systemctl enable`, пакету они не принадлежат и сами не удалятся. Поэтому:

- prerm останавливает все запущенные инстансы (`systemctl stop 'logstat@*.service'`) — только при реальном удалении, при обновлении инстансы не трогаются и поднимаются в postinstall;
- postrm при удалении пакета проходит по `.wants`-каталогам, снимает осиротевшие симлинки и делает `daemon-reload`.

Для чистоты всё же лучше сделать это самому до удаления:

```sh
sudo systemctl disable --now logstat@app1.service
sudo apt-get remove logstat     # или: sudo rpm -e logstat
```

Пользователь `logstat` и файлы `/etc/logstat/*.yaml`, созданные администратором, при удалении не трогаются.

## Счётчик перестал расти

Чеклист для дежурного, от самой дешёвой проверки к дорогой. Всё ниже — только
чтение.

1. **Демон вообще жив?** `systemctl status logstat@<инстанс>` — юнит
   перезапускается сам, поэтому цикл падений виден по растущему счётчику
   рестартов.
2. **Тот ли файл он читает?** Стартовая запись называет путь:
   `journalctl -u logstat@<инстанс> | grep starting`. Демон, ждущий так и не
   появившийся файл, пишет `log file does not exist yet`.
3. **Строки вообще приходят?** При включённом экспортере
   `logstat_lines_read_total` растёт, даже когда ничего не совпадает. Если он
   стоит — демон не читает строк: смотрите на источник лога, ротацию и права на
   чтение (`SupplementaryGroups`).
4. **Строки совпадают?** Сравните `logstat_matched_lines_total` с
   `logstat_lines_read_total`; обычная причина расхождения — опечатка в слове
   или регистр ([регистрозависимость](#регистрозависимость)). `logging.level:
   debug` печатает каждую совпавшую строку и закрывает вопрос — ценой записи на
   строку.
5. **Буфер застрял?** Растущий `logstat_pending_increments` при стоящем
   `logstat_redis_counter` означает, что строки посчитаны, но до Redis не
   доходят: смотрите `logstat_redis_up` и предупреждение `redis unavailable` в
   логе.
6. **Счётчик обнулили снаружи?** `logstat_redis_counter`, упавший в ноль не по
   расписанию, — это либо внешний `logstat clear`, либо истёкший ключ
   ([TTL на ключи](#ttl-на-ключи)), либо два инстанса на общем Redis с
   пересекающимися `actions` ([предупреждения оператору](#предупреждения-оператору)).

Без экспортера те же вопросы закрываются `redis-cli get
logstat:counter:<host>:<action>` с интервалом в минуту и логом демона на уровне
`debug`.


Внешние сервисы не нужны: Redis подменяется на [miniredis](https://github.com/alicebob/miniredis), лог-файлы создаются во временных каталогах. Покрыты матчинг (подстрока, оба режима регистра, счёт по строке, префиксные пересечения), парсер и валидатор конфига (включая дефолт `case_sensitive`, его предупреждения и сквозной прогон демона в регистронезависимом режиме), формирование ключей и форматной строки, сборка `lines=<N>` из ответа `INCRBY`, режим `heartbeat_key: false`, проставление и продление TTL на обоих ключах (включая истечение брошенного ключа и снятие TTL при `ttl: 0`), расчёт времени следующего срабатывания cron-расписаний, tail с обеими схемами ротации, старт при отсутствующем лог-файле, поведение при недоступном Redis и досброс после восстановления, сброс счётчиков (и напрямую, и через планировщик на расписании «каждую секунду», без ожидания реального cron), фильтрация уровней логирования и переоткрытие лог-файла, единственность экземпляра через `flock` и graceful shutdown по реальному `SIGTERM` в отдельном процессе. Две вещи, до которых Go-тесты не дотягиваются, закрыты иначе. `make fuzz` бросает произвольный YAML в парсер и валидатор конфига, чей контракт — на любой ввод отдать конфигурацию или ошибку, но никогда не панику: при `Restart=always` паника здесь означает цикл перезапусков. `make soak` гоняет кандидата против настоящего лога, настоящего Redis и настоящих часов столько, сколько скажете (`DURATION=24h`), по очереди ротируя файл обеими схемами и печатая RSS, счётчики и сбросы каждые 30 секунд; сам набор тестов не работает дольше полуминуты и подменяет время. CI добавляет слой ниже бинарника: `.deb` ставится на настоящую VM с systemd, поднимается шаблонным юнитом, переустанавливается поверх себя и удаляется — с проверкой maintainer-скриптов на каждом шаге, а `.rpm` ставится и удаляется в контейнере Fedora.

Экспортер покрыт с обеих сторон: коллектор на фиктивных часах (uptime, все значения конфига, серии по словам с нуля, монотонность итогов при дренаже буфера, отсутствие пароля в выдаче) и эндпоинт по настоящему HTTP (`200` на настроенном пути и `404` на любом другом, значения вслед за miniredis, `logstat_redis_up 0` при недоступном Redis, статус-страница на корне, отсутствие сокета при выключенном экспортере, фатальный старт на занятом порту и падение демона вслед за умершим на ходу экспортером).
